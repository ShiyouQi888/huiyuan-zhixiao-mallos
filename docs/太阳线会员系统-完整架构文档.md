# 一、系统概述

## 1.1 业务模型

以会员礼包为入口、以商品PV为计酬基础的会员分销系统。会员购买礼包获得资格与档位权益通，通过推广获得直推奖励；团队PV每日累加达标后自动升级，按职级费率获得团队奖、平级奖、领导奖，高层级另享全网分红池。

**PV计酬口径（2026-11-17 起）**：商品与会员档位分别配置整数PV；商品订单PV = 商品单件PV × 数量，档位新购 / 复消PV = 档位PV，升级PV = 目标档位PV − 当前档位PV。新订单的PV在下单时快照，商品价格、订单金额和钱包支付仍按人民币计算；会员普通商品订单支付成功后按订单PV × 3增加权益通，不消耗权益通。支付成功时写入业绩；奖金基数按 **1 PV = ¥1**，奖金 = PV × 对应比例。规则启用前的历史订单、业绩、等级记录和已生成奖金计划不重算；迁移将已有订单的PV快照设为原订单金额，保证历史数值不变。档位PV需随等级递增，以支持升级差额计酬。

**系统边界**：

| 项 | 状态 |
|---|---|
| 退款 | **不支持**，订单支付后不可退 |
| 提现 | **不支持**，奖金只能平台内消费或转给他人 |
| 资金流出 | **无**，平台只有资金流入 |
| 会员间转账 | 支持（钱包余额 / 太阳值）；钱包转出受权益通限制 |

## 1.2 角色

| 角色 | 定义 | 收益来源 |
|---|---|---|
| 普通用户 | 已注册未购买礼包 | 无 |
| 会员 | 已购买礼包 | 权益通、直推奖 |
| 高等级会员 | 团队累计PV达门槛自动升级 | 增加团队奖、平级奖、领导奖、分红池 |
| 运营 | 平台员工 | — |

## 1.3 五条收益线

| 线 | 触发条件 | 计算依据 | 频次 |
|---|---|---|---|
| 直推奖 | 推荐他人购买礼包 | 被推者订单PV × 对应比例 | **先拆后分期**：太阳值支付即入账，现金部分分期释放 |
| 团队奖 | 伞下产生新增PV | 自己伞下当日新增PV × 自己费率 | 日结 |
| 平级奖 | 直推下级追平或超过自己 | 下级当日团队奖 × 100% | 日结 |
| 领导奖 | 直推下级产生团队奖 | 下级当日团队奖 × 50% | 日结 |
| 分红池 | 等级恰好为副总/总经理/总裁 | 全网当日PV × 比例 ÷ 该级人数 | 日结 |

## 1.4 三类资产与权益通账户

| 资产 / 账户 | 来源 | 用途 | 有效期 | 可转账 | 可提现 |
|---|---|---|---|---|---|
| 权益通 | 支付成功的礼包订单与会员普通商品订单（订单PV × 3） | 仅随钱包会员间转出而消耗；商品消费不扣减 | 不过期；礼包复消可追加 | 本身不可转移 | ❌ |
| 钱包余额 | 奖金的 70% | 消费支付、会员间转账 | 永久 | ✅ | ❌ |
| 太阳值 | 奖金的默认 30%（可配置） | 虚拟资产记账 / 系统内会员互转 | — | ✅（即时到账） | ❌ |

权益通不是钱包余额，也不能用于支付订单。账户按 `granted / adjustedOut / used / reserved` 记录累计发放、后台调减、已消耗和待确认预占；可用权益通为 `max(granted - adjustedOut - used - reserved, 0)`。礼包新购与复消按档位PV × 3发放，升级按新旧PV差额 × 3补发；会员普通商品订单支付成功后按订单商品总PV × 3发放。商品消费不扣减权益通。仅会员间钱包转出按实际金额计入消耗；收到转账与获得奖励不消耗。转出金额不得超过可用额度；待确认钱包转账先预占，拒绝或超时释放，接收方确认后计为已用。旧规则计入的商城消费通过规则修订流水返还额度并保留审计记录。权益通用完不影响奖金结算。

# 二、业务规则

## 2.1 会员档位

| 档位 | 礼包价（元） | 默认PV | 权益通 | 有效期 |
|---|---|---|---|
| 银卡 | 2,000 | 2,000 | 6,000 | 12 个月 |
| 金卡 | 5,000 | 5,000 | 15,000 | 12 个月 |
| 钻卡 | 10,000 | 10,000 | 30,000 | 12 个月 |
| 至尊卡 | 20,000 | 20,000 | 60,000 | 12 个月 |

默认PV为初始化值，可在后台按档位独立调整；调整后只影响新订单。低等级到高等级的PV不得下降。

礼包权益通 = **档位PV × 3**。例如档位PV为 2,000 的银卡授予 6,000 权益通；会员普通商品订单权益通 = **订单商品总PV × 3**。权益通仅约束钱包会员间转出，不是可消费余额或可提现资金。

## 2.2 直推奖

**规则：先拆，后分期。**

1. **先拆**：计划创建时把直推奖总额按 `bonus.cash_ratio`（默认 70%）拆成两部分
   - 现金部分 → 进钱包，参与分期释放
   - 太阳值部分 → **支付成功即一次性入账**（`token_lots`），不参与分期、不重复发放
2. **后分期**：现金部分再按档位配置的期数均分，**余数补最后一期**，保证

   ```
   Σ各期金额 === 现金部分总额
   现金部分 + 太阳值部分 === PV × 直推比例
   ```

- 奖励总额 = 被推者订单PV × 档位直推比例（例：PV 1601 × 0.25 = 400.25 → 取整 400）
- 起点：被推者订单支付成功次日 00:00（UTC 口径）
- 期数取档位 `directReleaseDays`，未配置时读 `bonus.direct_periods`（默认 20）
- 系统无退款，因此**不存在中止场景**，计划一定跑完

| 直推奖总额 | 现金（70%） | 太阳值（30%） | 期数 | 每期现金 | 末期 |
|---|---|---|---|---|---|
| 2,000 | 1,400 | 600 | 20 | 70 | 70 |
| 1,000 | 700 | 300 | 20 | 35 | 35 |
| 400 | 280 | 120 | 3 | 93 | 94（余数补齐）|

> **历史计划兼容**：`bonus_plans.split_at` 为空表示旧规则计划（全额分期、逐期再拆 70/30），
> 其到期期次按旧口径释放，避免重复发放太阳值；旧实现因整数除法截断产生的少付差额，
> 由 `scripts/backfill-direct-plan.ts` 输出补偿清单并按 `--apply --compensate` 补齐。

## 2.3 团队奖

```
团队奖 =（自己伞下当日新增PV − 符合条件时的最大推广线PV）× 自己的职级费率
```

- 伞下 = 自己推荐的所有人及其下级，无限层
- 新增PV = **当日**新完成订单快照的PV
- 各人按自己等级费率计算，互不扣减
- 每位会员单独剔除自己直属推广线中当日团队PV最大的一条线；至少有 2 条有效直属会员线才剔除，单线不剔除。可设置占比阈值，默认 0 表示符合条件即剔除
- 被剔除线的子树PV不计入该会员团队奖基数；该条直接上下级关系不产生领导奖/平级奖，线内其他会员仍按各自的最大推广线规则计算
- 平台账号不参与推广线候选；最大线并列时按下级账号 ID 升序取第一条，保证日结结果稳定
- 管理后台在会员等级中配置团队奖费率，在「奖金参数设置」中管理最大推广线剔除开关和占比阈值
- 权益通状态不参与奖金资格判断；额度用完后，奖金仍按现有规则正常结算

## 2.4 等级体系

| 等级 | level | 达标门槛（团队**累计PV**） | 团队奖费率 | 分红池 |
|---|---|---|---|---|
| 普通会员 | 0 | — | 0 | — |
| 业务主任 | 1 | 5 万 | 3% | — |
| 业务经理 | 2 | 30 万 | 6% | — |
| 业务总监 | 3 | 100 万 | 9% | — |
| 业务副总 | 4 | 300 万 | 12% | 全网 2% |
| 业务总经理 | 5 | 600 万 | 15% | 全网 2% |
| 业务总裁 | 6 | 1,000 万 | 18% | 全网 1% |

**规则**：

- **每日统计**：日结时把当日团队PV累加到 `users.total_team_performance`
- **历史累计**：从注册至今的总和，不按月重置
- 按累计值判定等级，`newRank = max(当前, 应得)`
- **只升不降**：达到后永久保留

## 2.5 平级奖

**触发条件**：直推下级等级**追平或超过**自己。首次满足即**永久锁定**。

```
平级奖 = 该直推下级当日团队奖 × 100%
```

| 项 | 规则 |
|---|---|
| 判定 | `上级.level <= 下级.level` |
| 锁定 | 首次满足置位 `peer_bonus_locked`，之后不再判定 |
| 基数 | 下级当日团队奖 |
| 层级 | 仅直推 1 代 |

**完整示例**（B 每日团队奖固定 1,000）：

| 阶段 | A 等级 | B 等级 | 判定 | 锁定 | A 平级 | A 领导 | 合计 |
|---|---|---|---|---|---|---|---|
| ① | 主任(1) | 普通(0) | 1≤0 ❌ | 否 | 0 | 500 | 500 |
| ② | 主任(1) | 主任(1) | 1≤1 ✅ | **是** | 1,000 | 500 | 1,500 |
| ③ | 主任(1) | 总监(3) | B 超过 | 是 | 1,000 | 500 | 1,500 |
| ④ | 副总(4) | 总监(3) | A 反超 | 是 | 1,000 | 500 | 1,500 |

**为什么锁定**：等级只升不降，若按"当前同级"判定，任一方升级都会让另一方收入断崖下跌。

## 2.6 领导奖

```
领导奖 = 直推下级当日团队奖 × 50%
```

- 基数：下级当日团队奖（用**下级**的费率）
- 层级：仅直推 1 代
- 与平级奖**叠加**：锁定后合计 150%，未锁定则只有 50%

## 2.7 全网分红池

```
每日：池子 = 全网当日PV × 该级比例（1 PV = ¥1）
      每人 = 池子 ÷ 当日该级人数
```

| 等级 | 比例 | 参与人 |
|---|---|---|
| 业务副总 | 2% | 当前等级**恰好等于**副总 |
| 业务总经理 | 2% | 当前等级**恰好等于**总经理 |
| 业务总裁 | 1% | 当前等级**恰好等于**总裁 |

**关键口径**：按"等级 = 该级"判定，一人只进一个池。

**由此产生的现象**：升到总经理即退出副总池。若总经理池人均低于副总池，升级会降收。这是规则选择的必然结果，运营需知悉。

**人数为 0 时**：池子不分配，沉淀为平台留存，记录在 `rank_snapshots`。

## 2.8 复消与权益通

权益通与复消按以下规则处理：

```
可用权益通 = max(累计发放 - 后台调减 - 已消耗 - 待确认预占, 0)
已用达到发放额度扣除后台调减额 → 可复消礼包
礼包新购/复消支付成功 → 增加档位PV × 3
升级支付成功 → 增加档位PV差额 × 3
会员普通商品订单支付成功 → 增加订单商品总PV × 3
```

仅会员间钱包转出按实际金额消耗权益通；新发起的转出金额不得超过可用额度，超额请求会被拒绝。商城商品订单使用钱包付款不消耗权益通，也不受可用额度限制。会员普通商品订单支付成功后均按商品总PV × 3新增权益通。礼包新购/复消按档位PV × 3发放，升级按新旧档位PV差额 × 3补发。旧规则已计入的商城消费额度由规则修订退回并保留审计流水。收到转账和奖励入账不会消耗权益通。权益通用完不影响团队奖、平级奖、领导奖、分红池与直推奖正常发放；会员订单业绩也照常向上归集。

**复消订单的奖励**：

| 奖励 | 规则 |
|---|---|
| 直推奖 | 被推者档位PV × **复消直推比例** |
| 团队奖 / 平级奖 / 领导奖 | 全额正常计算 |
| 分红池 | 计入当日全网计酬PV |

复消只增加权益通，不影响奖金发放资格，也不存在暂停期间奖金的补发处理。

## 2.9 无出局

系统不存在出局概念，无累计奖金上限，无封顶。

## 2.10 奖金拆分

每笔奖金入账时按比例拆分：

| 部分 | 比例 | 去向 | 说明 |
|---|---|---|---|
| 现金余额 | 70% | `wallets` | 可消费、可转账，**不可提现** |
| 太阳值 | 默认 30%（可配置） | `token_lots` | 虚拟资产记账；支持系统内互转，未接入外部交易 |

```
某日奖金 10,000
  钱包余额 += 7,000
  太阳值记账 += 3,000
```

**拆分时点**：

- **直推奖**：「先拆后分期」——计划创建（支付成功）时即完成拆分，太阳值一次性入账，现金再分期释放；
- **其余奖金（团队/平级/领导/分红）**：入账时按 70/30 一次拆分完成，钱包余额天然就是可用口径。

## 2.11 会员间转账

**支持钱包余额和太阳值转账**：

| 资产 | 可转 | 说明 |
|---|---|---|
| 钱包余额 | ✅ | 仅转出消耗转出方权益通；商城商品消费不消耗；待确认转账会先预占 |
| 太阳值 | ✅ | 即时到账，创建即完成 |

**共同规则**：

| 项 | 规则 |
|---|---|
| 双方要求 | 均已注册；转出方已实名 |
| 限额 | 可配置，默认不限 |
| 手续费 | 无 |
| 确认 | 钱包余额转账由接收方 24h 内确认，超时自动退回；太阳值即时到账 |
| 风控 | 同设备互转、高频互转、新号大额 → 拒绝或人工审核 |

发起钱包余额或太阳值转账前，会员须设置并验证独立的 6 位转账支付密码。钱包余额转出还须有足够的档位权益通。密码以 bcrypt 哈希保存；连续验证失败 5 次后锁定 15 分钟。修改已设置密码时须验证当前密码。忘记密码需通过平台身份核验流程重置。

**转账与业绩的关系（已确认）**：

```
转账行为本身不产生业绩，也不改变业绩归属。
用转账所得余额支付的订单，与用自有余额支付的订单完全一样，业绩照常计算。
```

| 场景 | 业绩处理 |
|---|---|
| A 转 1,000 给 B，B 用这 1,000 买礼包 | B 的业绩 **+1,000**，正常向上归集 |
| B 用自有充值款买礼包 | B 的业绩 +1,000，正常向上归集 |
| A → B → C 连续转账后 C 下单 | C 的业绩正常计入，A 和 B 的转账行为不额外产生业绩 |

**说明**：系统不追踪"这笔余额是谁转来的"。订单业绩只认下单人（`users.id`），由树形归集向上累加，与余额来源无关。

## 2.12 收货地址

会员可在账户设置中新增、编辑、删除和设置默认收货地址；地区使用内置省、市、区县级联选择，联系电话校验为有效的 11 位大陆手机号。东莞、中山、儋州、嘉峪关等不设县级区划的城市允许不填写区县。实物商品下单必须选择本人地址；创建订单时将收货人、电话及完整地址复制为订单快照，之后修改地址簿不会改变已提交订单的配送信息。会员订单页和管理后台订单详情均展示该快照。

## 2.13 虚拟货币发行

**所有虚拟货币均由平台发行**，转账只是账户间转移，不产生新币。

| 资产 | 发行时点 | 发行量 | 回收时点 |
|---|---|---|---|
| 权益通 | 礼包购买、升级补差、礼包复消、会员普通商品订单 | 礼包PV × 3；升级PV差额 × 3；商品订单PV × 3 | 仅钱包会员间转出时消耗；无提现 |
| 钱包余额 | 每笔奖金入账 | 奖金 × 70% | 消费支付、会员间转账 |
| 太阳值 | 每笔奖金入账 | 奖金 × 30% | 不回收（永久记账） |

权益通属于业务限制账户，不属于资金发行量。

**平台可查询的资金与太阳值总量**：

| 指标 | 计算口径 |
|---|---|
| 累计发行量 | Σ 钱包与太阳值的发放流水 |
| 流通量 | 当前各账户余额之和 |
| 已消费/已过期量 | Σ 消费 + Σ 过期 |
| 沉淀量 | 累计发行 − 流通 − 已消费 |

**约束**：

- 只有平台服务能调用发放接口，任何用户侧接口不得直接增加余额
- 转账只在账户间转移，转出方扣减 = 转入方增加，总量不变
- 每笔发行必须关联来源单据（订单 ID / 奖金记录 ID），可追溯

# 五、核心流程

## 5.1 注册与绑定

```
扫码/点链接 → 解析推荐码
   ↓
校验推荐人 status = 0
   ↓
写 users：parent_id / path / depth / rank_level = 0
   ↓
注册成功
```

**边界**：推荐人不存在或注销 → `parent_id = NULL`；绑定后不可变更，换绑需审批。

## 5.2 下单

### 5.2.1 订单状态机（简化为 4 态）

```
CREATED（待支付）
   ├─ 支付成功 → PAID（同一事务登记业绩、档位、权益通与直推计划）
   └─ 30 分钟未付 → CANCELLED
        ↓
PAID（已付款待发货；业务效果已入账）
   ↓ 后台录入快递公司与快递单号并确认发货
DELIVERED（已发货）
   ↓ 用户确认收货 或 T+10 自动
COMPLETED（终态；只更新订单状态）
```

**无退款**，因此无 REFUNDING / REFUNDED。支付成功时按订单PV写业绩并创建相应权益、奖励计划；团队奖金进入日结，直推计划在支付时先拆出太阳值与现金，太阳值一次性入账，现金按配置分期释放。DELIVERED 状态保存物流公司、单号和发货时间；COMPLETED 不重复产生账务影响。

### 5.2.2 四类订单

| type | 场景 | 人民币订单金额 | 计酬PV | 直推奖基数 |
|---|---|---|---|---|
| 1 新购 | 首次买礼包 | 档位售价 | 档位PV | 档位PV × 新购比例 |
| 2 升级 | 低档升高档 | 售价差额 | 目标档位PV − 当前档位PV | PV差额 × 升级比例 |
| 3 复消 | 档位权益通已用完后再买 | 档位售价 | 档位PV | 档位PV × 复消比例 |
| 4 普通商品 | 会员商城购物 | 商品有效售价 × 数量 | 商品单件PV × 数量 | 会员商品订单PV × 3权益通 |

新订单PV在下单时快照。支付成功即写入业绩，日结基于这些PV计算团队奖与分红，且1 PV按¥1计奖金基数；实际支付与钱包余额始终按人民币金额处理，普通商城消费不消耗权益通，会员普通商品订单支付成功后均按PV × 3增发权益通。直推奖计划在支付时建立：先按 `bonus.cash_ratio` 拆出现金与太阳值，太阳值一次性入账、不参与分期，现金按档位配置分期释放且余数补最后一期。商品档位专属价不改变PV。PV规则切换前的历史订单、历史业绩、已生成奖金计划和会员等级不回算。

### 5.2.3 支付方式

```
订单总额 amount
   ↓
可用：钱包余额（不含冻结）
   ↓
不足部分 → 无现金支付通道，直接报错
   ↓
amount = balance_deduct + cash_pay(0)
```

`equity_deduct` 为历史兼容字段，新订单固定为 0。权益通不抵扣订单金额；商城商品订单只受钱包可用余额约束，不检查或扣减权益通。PV规则切换后的会员 type=4 商品订单在支付成功后按订单PV × 3新增权益通。

## 5.3 升级流程

```
选择升级档位
   ↓
差价 = 新档位价格 - 当前档位价格
计酬PV = 新档位PV - 当前档位PV
   ↓
创建 orders（type=2, amount=差价, from_package_id=旧档位）
   ↓
支付成功 → 同一事务完成业务记账
   ├─ users.package_id = 新档位
   ├─ 补发权益通：新档位额度 - 旧档位额度（已用额度不回收）
   ├─ 创建直推奖计划：升级PV × 直推比例，按配置期数释放
   └─ 写入升级业绩 = 升级PV，纳入后续日结
后台发货时登记快递公司与单号；确认收货只更新订单状态
```

**举例**：

```
银卡售价 2,000 / PV 1,500（标准权益通 4,500，已用 2,000，剩余 2,500）→ 金卡售价 5,000 / PV 4,200

订单金额   = 3,000
升级PV     = 4,200 - 1,500 = 2,700
权益通补发 = (4,200 - 1,500) × 3 = 8,100
升级后权益通余额 = 2,500 + 8,100 = 10,600
直推奖     = 2,700（比例 100% 时，按配置期数释放）
计酬业绩   = 2,700 PV
```

## 5.4 每日奖金计算

### 5.4.1 主流程

```
每日 02:00（锁 lock:job:daily_settle:{date}）

Step 0  初始化结算批次（记录 step，支持断点续跑）
Step 1  幂等检查
Step 2  补齐昨日已支付订单 → 按 paid_at 写 order_performance
Step 3  树形归集 → 写 team_performance
Step 4  等级判定 → 更新 rank_id / rank_level / total_team_performance
Step 5  写 rank_snapshots（各等级人数 + 全网计酬PV + 池子）
Step 6  计算团队奖
Step 7  计算平级奖 + 领导奖（自底向上）
Step 8  计算分红池
Step 9  拆分 70/30 → 写 wallet_transactions + token_lots
Step 10 标记完成
Step 11 通知
```

### 5.4.2 树形归集

```typescript
function aggregateTeam(
  users: { id: number; parentId: number | null; depth: number }[],
  own: Map<number, number>,
): Map<number, number> {
  const team = new Map<number, number>();
  // 必须按 depth 降序：子节点算完才传给父节点
  for (const u of [...users].sort((a, b) => b.depth - a.depth)) {
    const cur = (team.get(u.id) ?? 0) + (own.get(u.id) ?? 0);
    team.set(u.id, cur);
    if (u.parentId !== null) {
      team.set(u.parentId, (team.get(u.parentId) ?? 0) + cur);
    }
  }
  return team;
}
```

### 5.4.3 等级判定

```typescript
const total = user.totalTeamPerformance + todayTeamAmount;
const eligible = ranks.filter(r => total >= r.threshold).pop();
const newRankId = Math.max(user.rankId, eligible?.id ?? 0);   // 只升不降

}

```

### 5.4.4 团队奖

```
对每个 rank_level > 0：
    excluded_line = 本人的最大直属会员推广线（直属有效会员少于 2 人则为空）
    effective_amount = team_amount - (excluded_line?.team_amount ?? 0)
    团队奖 = effective_amount × rank.team_rate
```

### 5.4.5 平级奖 + 领导奖

```
按 depth 从深到浅遍历：

对每个 X：
  teamBonus = X.团队奖有效基数 × X.费率

  P = X.parent_id
  if P 且 P→X 不是 P 被剔除的最大推广线:

    // 平级奖：首次满足即锁定
    if !X.peer_bonus_locked && P.rank_level <= X.rank_level:
        X.peer_bonus_locked = true
        X.peer_bonus_locked_at = now()
        audit('PEER_LOCK', X.id, P.id)

    if X.peer_bonus_locked:
        P.peer += teamBonus × 1.00

    // 领导奖
    P.leader += teamBonus × 0.50
```

**三个易错点**：顺序不能反（基数依赖下级）；锁定必须持久化；权益通状态不参与奖金资格判断。最大线只排除对应的直属关系奖励，线内会员仍按自己的最大推广线规则计算。

### 5.4.6 分红池

```
G = 当日全网计酬PV（按 1 PV = ¥1 换算奖金基数）
for rank where pool_rate > 0:
    count = 当日该级人数（快照）
    pool  = G × pool_rate
    perCapita = count > 0 ? pool / count : 0

对每个该级用户：分红 = perCapita
```

### 5.4.7 算例

```
全网当日计酬PV 1,000 万（该算例假设 A、B 均只有一条有效直属会员线，因此不触发最大线剔除）

A：总监(9%)，团队当日 10 万 → 团队奖 9,000
B：总监(9%)，团队当日 3 万，B 是 A 的直推且已锁定
   B 团队奖 = 2,700
   A 平级 = 2,700；A 领导 = 1,350；合计 4,050
C：副总(12%)，副总池 = 20 万，副总 10 人 → 分红 2 万
```

## 5.5 复消流程

```
钱包转出确认 → transfer_quota_accounts.used 增加实际转出金额
  → 可用权益通 = max(granted - adjusted_out - used - reserved, 0)
  → used >= granted - adjusted_out 时允许发起复消；奖金结算保持正常

礼包复消 → orders(type=3, is_repurchase=true)
  → 支付成功：更新档位、发权益通、创建直推计划并写业绩
  → transfer_quota_accounts.granted += 所选档位PV × 3
  → 直推奖按 10% 创建计划
  → 业绩正常归集

会员普通商品订单 → 会员创建 orders(type=4, is_repurchase=true)
  → 支付成功：写业绩并发权益通
  → transfer_quota_accounts.granted += 订单商品总PV × 3
```

会员普通商品订单支付成功后按订单总PV × 3发放。礼包复消支付成功后按档位PV × 3发放；升级支付成功后按档位PV差额 × 3补发。

**边界**：仅已确认的钱包转出消耗权益通；普通商城消费、订单支付、钱包转入、奖金入账均不消耗。普通商城订单只受钱包可用余额约束。待确认钱包转账预占权益通，拒绝或过期后释放。

## 5.6 资产转账

### 5.6.1 权益通检查

```
创建钱包转账时校验：钱包可用余额 ≥ 转账额，且可用权益通 ≥ 转账额
   ↓
额度预占；钱包余额冻结；创建 wallet_transfers（PENDING）
   ↓
接收方确认：预占转入 used；冻结金额转入接收方钱包
   ↓
拒绝或超时：释放预占额度并解冻钱包余额
```

### 5.6.2 钱包余额转账

```
输入对方手机号 + 金额
   ↓
校验：双方正常、转出方实名、余额足够
   ↓
balance -= amount, frozen += amount
   ↓
创建 wallet_transfers（PENDING）
   ↓
接收方确认（24h）
   ↓
转出方 frozen -= amount，入方 balance += amount
   ↓
双方写流水，状态 COMPLETED
```

**超时**：24h 未确认 → `EXPIRED`，退回转出方。

**风控规则**：

| 规则 | 阈值 | 动作 |
|---|---|---|
| 同设备互转 | 双方设备指纹相同 | 拒绝 |
| 高频互转 | 7 天内同一对账户 ≥3 次 | 人工审核 |
| 集中转入 | 24h 内收到 ≥3 人转入 | 人工审核 |
| 新号大额 | 注册 <7 天且单笔 >5,000 | 人工审核 |

# 六、关键机制

## 6.1 幂等

| 场景 | 幂等键 |
|---|---|
| 直推奖释放 | `UNIQUE(plan_id, period_no)` + `UNIQUE(biz_type, biz_id)` |
| 日结业绩 | `UNIQUE(user_id, stat_date)` |
| 分红 | `UNIQUE(stat_date, user_id)` |
| 钱包入账 | `UNIQUE(biz_type, biz_id)` |
| 档位权益通 | `UNIQUE(biz_type, biz_id)` |
| 转账 | `transfer_no` + `idempotency_keys` |

## 6.2 快照一致性

日结三类快照，开始时锁定、全程复用：

| 快照 | 表 | 风险 |
|---|---|---|
| 当日订单 | `order_performance` | 中途出现新支付订单 |
| 各等级人数 + 全网计酬PV | `rank_snapshots` | 中途有人升级 |
| 各人团队计酬PV | `team_performance` | 中途新PV |

**窗口**：以自然日 `occur_date` 为界，02:00 处理前一天。

## 6.3 断点续跑

```
settle_batches：id, stat_date, step, status(RUNNING/DONE/FAILED), started_at, finished_at

Step 0 写批次(step=0)
每步完成更新 step
崩溃重启：从 batch.step 继续
```

**必须可重入**：每步重复执行结果一致（依赖幂等键）。

## 6.4 并发控制

| 场景 | 手段 |
|---|---|
| 日结 | Redis 锁 TTL 2h + DB 唯一键 |
| 余额扣减 | `UPDATE ... WHERE balance >= X AND version = ?` |
| 权益通 | 乐观锁 + 可用额度校验；待确认时预占 |
| 平级奖锁定 | `SELECT ... FOR UPDATE` |
| 转账 | 乐观锁 + 状态机 |

## 6.5 账务对账（每日 04:00）

```
① Σ(bonus_records.cash_amount) = Σ(wallet_transactions where type=1)
② Σ(bonus_records.token_amount) = Σ(token_lots.amount)
③ Σ(wallet_transactions.change_amount) = Σ(wallets.balance)（冻结在发起转账时已扣余额并落流水，故不计入）
④ Σ(wallets.frozen) = Σ(status='PENDING' 的钱包转出金额)
⑤ Σ(dividends.amount) ≤ Σ(rank_snapshots.pool_amount)
⑥ 权益通 `available = max(granted - adjusted_out - used - reserved, 0)`；used 与已完成钱包转出核对，reserved 与待确认钱包转出核对
⑦ 直推奖计划自洽：`Σ(bonus_stages.amount) = bonus_plans.total_amount` 且 `released_amount = Σ(已释放期次金额)`（只对新规则计划严格，历史计划差异由补偿脚本处理）
任一不等 → 告警
```

## 6.6 监控指标

| 指标 | 阈值 | 动作 |
|---|---|---|
| 日结耗时 | > 10 分钟 | 告警 |
| 日结失败 | 任一 | 立即告警 |
| 对账差异 | > 0 | 告警 |
| 奖金支出 / 当日计酬PV | > 60% | 预警 |
| 转账风控命中率 | 突增 300% | 告警 |
| 单日新增会员 | 环比 > 300% | 风控告警 |

## 9.2 可用性

## 9.3 安全

HTTPS；手机号/身份证 AES-256-GCM 加密；RBAC；资金操作全审计；日志脱敏。

## 9.4 测试要求

**必测场景**：

- [ ] 同一分期并发触发 10 次，只入账 1 次
- [ ] 日结中断后从断点续跑，结果与一次跑完一致
- [ ] 平级奖锁定后，双方任意升级都不影响发放
- [ ] 权益通耗尽不影响奖金结算；复消支付成功后追加权益通
- [ ] PV规则切换后，会员普通商品订单支付成功后按订单PV × 3发放权益通
- [ ] 分红池某等级人数为 0 时不除零
- [ ] 钱包转出预占额度、确认转为已用、拒绝或超时正确释放
- [ ] 升级补发档位权益通差额正确
- [ ] 钱包余额转账在确认前不扣减、超时正确退回
- [ ] 同一资产并发转账，不出现负余额
- [ ] 用转账所得余额下单，业绩正常计入（不追踪余额来源）
- [ ] 开关关闭后前端入口隐藏、后端接口拒绝
- [ ] 分端开关在不同 platform 下表现正确、分级开关按等级过滤

## 11.2 术语

| 术语 | 说明 |
|---|---|
| 伞下 | 自己推荐的所有人及其下级，无限层 |
| 团队业绩 | 伞下所有会员计酬PV之和 |
| 团队奖 | 伞下当日新增计酬PV × 自己职级费率 |
| 平级奖 | 直推下级追平或超过自己时触发，永久锁定 |
| 领导奖 | 直推下级团队奖的 50% |
| 分红池 | 全网当日计酬PV × 比例 ÷ 该级人数；1 PV = ¥1 奖金基数 |
| 复消 | 权益通用完后可复消礼包；按档位PV × 3追加额度，不改变奖金结算资格 |
| 权益通 | 礼包和会员商品订单按PV发放；仅随会员间钱包转出减少，不可提现 |
| 太阳值 | 奖金默认 30%，作为虚拟资产记账并支持会员间系统内互转（即时到账） |
| 只升不降 | 等级达到后永久保留 |
