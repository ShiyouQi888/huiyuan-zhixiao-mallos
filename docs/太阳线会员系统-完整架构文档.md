# 一、系统概述

## 1.1 业务模型

以会员礼包为入口、以团队业绩为计酬基础的会员分销系统。会员购买礼包获得资格与权益值，通过推广获得直推奖励；团队业绩每日累加达标后自动升级，按职级费率获得团队奖、平级奖、领导奖，高层级另享全网分红池。

**系统边界**：

| 项 | 状态 |
|---|---|
| 退款 | **不支持**，订单支付后不可退 |
| 提现 | **不支持**，奖金只能平台内消费或转给他人 |
| 资金流出 | **无**，平台只有资金流入 |
| 会员间转账 | 支持（权益值 + 钱包余额） |

## 1.2 角色

| 角色 | 定义 | 收益来源 |
|---|---|---|
| 普通用户 | 已注册未购买礼包 | 无 |
| 会员 | 已购买礼包 | 权益值、直推奖 |
| 高等级会员 | 团队业绩达门槛自动升级 | 增加团队奖、平级奖、领导奖、分红池 |
| 运营 | 平台员工 | — |

## 1.3 五条收益线

| 线 | 触发条件 | 计算依据 | 频次 |
|---|---|---|---|
| 直推奖 | 推荐他人购买礼包 | 被推者礼包价 × 100% | 分 20 天释放 |
| 团队奖 | 伞下产生新增业绩 | 自己伞下当日新增业绩 × 自己费率 | 日结 |
| 平级奖 | 直推下级追平或超过自己 | 下级当日团队奖 × 100% | 日结 |
| 领导奖 | 直推下级产生团队奖 | 下级当日团队奖 × 50% | 日结 |
| 分红池 | 等级恰好为副总/总经理/总裁 | 全网业绩 × 比例 ÷ 该级人数 | 日结 |

## 1.4 三种资产

| 资产 | 来源 | 用途 | 有效期 | 可转账 | 可提现 |
|---|---|---|---|---|---|
| 权益值 | 购买/升级礼包（价 × 3） | 消费抵扣 | 12 个月 | ✅ | ❌ |
| 钱包余额 | 奖金的 70% | 消费支付 | 永久 | ✅ | ❌ |
| 数权 | 奖金的 30% | 仅记账 | — | ❌ | ❌ |

# 二、业务规则

## 2.1 会员档位

| 档位 | 礼包价（元） | 权益值 | 有效期 |
|---|---|---|---|
| 银卡 | 2,000 | 6,000 | 12 个月 |
| 金卡 | 5,000 | 15,000 | 12 个月 |
| 钻卡 | 10,000 | 30,000 | 12 个月 |
| 至尊卡 | 20,000 | 60,000 | 12 个月 |

**权益值 = 礼包价 × 3**，用于平台商品消费抵扣，可会员间互转，不可提现。

## 2.2 直推奖

| 被推者档位 | 直推奖总额 | 日释放额 | 释放天数 |
|---|---|---|---|
| 2,000 | 2,000 | 100 | 20 |
| 5,000 | 5,000 | 250 | 20 |
| 10,000 | 10,000 | 500 | 20 |
| 20,000 | 20,000 | 1,000 | 20 |

**规则**：

- 奖励 = 被推者礼包价 × 100%，分 20 天平均释放
- 日释放额 = 礼包价 ÷ 20
- 起点：被推者订单**完成**次日 00:00
- 系统无退款，因此**不存在中止场景**，计划一定跑完

## 2.3 团队奖

```
团队奖 = 自己伞下当日新增业绩 × 自己的职级费率
```

- 伞下 = 自己推荐的所有人及其下级，无限层
- 新增业绩 = **当日**新产生的业绩
- 各人按自己等级费率计算，互不扣减
- 暂停计酬状态不发放

## 2.4 等级体系

| 等级 | level | 达标门槛（团队**累计**业绩） | 团队奖费率 | 分红池 |
|---|---|---|---|---|
| 普通会员 | 0 | — | 0 | — |
| 业务主任 | 1 | 5 万 | 3% | — |
| 业务经理 | 2 | 30 万 | 6% | — |
| 业务总监 | 3 | 100 万 | 9% | — |
| 业务副总 | 4 | 300 万 | 12% | 全网 2% |
| 业务总经理 | 5 | 600 万 | 15% | 全网 2% |
| 业务总裁 | 6 | 1,000 万 | 18% | 全网 1% |

**规则**：

- **每日统计**：日结时把当日团队业绩累加到 `users.total_team_performance`
- **历史累计**：从注册至今的总和，不按月重置
- 按累计值判定等级，`newRank = max(当前, 应得)`
- **只升不降**：达到后永久保留

## 2.5 平级奖

**触发条件**：直推下级等级**追平或超过**自己。首次满足即**永久锁定**。

```
平级奖 = 该直推下级当日团队奖 × 100%
```

| 项 | 规则 |
|---|---|
| 判定 | `上级.level <= 下级.level` |
| 锁定 | 首次满足置位 `peer_bonus_locked`，之后不再判定 |
| 基数 | 下级当日团队奖 |
| 层级 | 仅直推 1 代 |

**完整示例**（B 每日团队奖固定 1,000）：

| 阶段 | A 等级 | B 等级 | 判定 | 锁定 | A 平级 | A 领导 | 合计 |
|---|---|---|---|---|---|---|---|
| ① | 主任(1) | 普通(0) | 1≤0 ❌ | 否 | 0 | 500 | 500 |
| ② | 主任(1) | 主任(1) | 1≤1 ✅ | **是** | 1,000 | 500 | 1,500 |
| ③ | 主任(1) | 总监(3) | B 超过 | 是 | 1,000 | 500 | 1,500 |
| ④ | 副总(4) | 总监(3) | A 反超 | 是 | 1,000 | 500 | 1,500 |

**为什么锁定**：等级只升不降，若按"当前同级"判定，任一方升级都会让另一方收入断崖下跌。

## 2.6 领导奖

```
领导奖 = 直推下级当日团队奖 × 50%
```

- 基数：下级当日团队奖（用**下级**的费率）
- 层级：仅直推 1 代
- 与平级奖**叠加**：锁定后合计 150%，未锁定则只有 50%

## 2.7 全网分红池

```
每日：池子 = 全网当日业绩 × 该级比例
      每人 = 池子 ÷ 当日该级人数
```

| 等级 | 比例 | 参与人 |
|---|---|---|
| 业务副总 | 2% | 当前等级**恰好等于**副总 |
| 业务总经理 | 2% | 当前等级**恰好等于**总经理 |
| 业务总裁 | 1% | 当前等级**恰好等于**总裁 |

**关键口径**：按"等级 = 该级"判定，一人只进一个池。

**由此产生的现象**：升到总经理即退出副总池。若总经理池人均低于副总池，升级会降收。这是规则选择的必然结果，运营需知悉。

**人数为 0 时**：池子不分配，沉淀为平台留存，记录在 `rank_snapshots`。

## 2.8 复消与暂停计酬

**状态机**：

```
ACTIVE ──权益值余额归零（用完或全部过期）──→ SUSPENDED
SUSPENDED ──复购任意礼包──→ ACTIVE
```

**暂停期间的范围**：

| 对象 | 是否发放 |
|---|---|
| 本人团队奖 | 停发 |
| 本人应得的平级奖 / 领导奖 | 停发 |
| 本人分红池份额 | **停发** |
| 本人业绩是否计入上级团队 | **计入** |
| 本人消费产生的业绩 | 计入并向上累加 |

**一句话**：停的是"他领钱"，不是"他的业绩"。业绩照常传递，他自己不产生收益。

**复消订单的奖励**：

| 奖励 | 规则 |
|---|---|
| 直推奖 | 被推者礼包价 × **10%** |
| 团队奖 / 平级奖 / 领导奖 | 全额正常计算 |
| 分红池 | 计入当日全网业绩 |

**恢复后不补发**暂停期间的奖金。

## 2.9 无出局

系统不存在出局概念，无累计奖金上限，无封顶。

## 2.10 奖金拆分

每笔奖金入账时按比例拆分：

| 部分 | 比例 | 去向 | 说明 |
|---|---|---|---|
| 现金余额 | 70% | `wallets` | 可消费、可转账，**不可提现** |
| 数权 | 30% | `token_lots` | 仅记账，不流转、不交易 |

```
某日奖金 10,000
  钱包余额 += 7,000
  数权记账 += 3,000
```

**拆分在入账时完成**，钱包余额天然就是可用口径。

## 2.11 会员间转账

**支持两种资产互转**：

| 资产 | 可转 | 说明 |
|---|---|---|
| 权益值 | ✅ | 有到期日，受让批次继承最早到期日 |
| 钱包余额 | ✅ | 永久有效 |
| 数权 | ❌ | 仅记账，不流转 |

**共同规则**：

| 项 | 规则 |
|---|---|
| 双方要求 | 均已注册；转出方已实名 |
| 限额 | 可配置，默认不限 |
| 手续费 | 无 |
| 确认 | 接收方 24h 内确认，超时自动退回 |
| 风控 | 同设备互转、高频互转、新号大额 → 拒绝或人工审核 |

发起钱包余额或权益值转账前，会员须设置并验证独立的 6 位转账支付密码。密码以 bcrypt 哈希保存；连续验证失败 5 次后锁定 15 分钟。修改已设置密码时须验证当前密码。忘记密码需通过平台身份核验流程重置。

**转账与业绩的关系（已确认）**：

```
转账行为本身不产生业绩，也不改变业绩归属。
用转账所得余额支付的订单，与用自有余额支付的订单完全一样，业绩照常计算。
```

| 场景 | 业绩处理 |
|---|---|
| A 转 1,000 给 B，B 用这 1,000 买礼包 | B 的业绩 **+1,000**，正常向上归集 |
| B 用自有充值款买礼包 | B 的业绩 +1,000，正常向上归集 |
| A → B → C 连续转账后 C 下单 | C 的业绩正常计入，A 和 B 的转账行为不额外产生业绩 |

**说明**：系统不追踪"这笔余额是谁转来的"。订单业绩只认下单人（`users.id`），由树形归集向上累加，与余额来源无关。

## 2.12 收货地址

会员可在账户设置中新增、编辑、删除和设置默认收货地址；地区使用内置省、市、区县级联选择，联系电话校验为有效的 11 位大陆手机号。东莞、中山、儋州、嘉峪关等不设县级区划的城市允许不填写区县。实物商品下单必须选择本人地址；创建订单时将收货人、电话及完整地址复制为订单快照，之后修改地址簿不会改变已提交订单的配送信息。会员订单页和管理后台订单详情均展示该快照。

## 2.13 虚拟货币发行

**所有虚拟货币均由平台发行**，转账只是账户间转移，不产生新币。

| 资产 | 发行时点 | 发行量 | 回收时点 |
|---|---|---|---|
| 权益值 | 礼包购买、升级补差 | 礼包价 × 3 | 消费抵扣、12 个月过期 |
| 钱包余额 | 每笔奖金入账 | 奖金 × 70% | 消费支付 |
| 数权 | 每笔奖金入账 | 奖金 × 30% | 不回收（永久记账） |

**平台可查询的四个总量**：

| 指标 | 计算口径 |
|---|---|
| 累计发行量 | Σ 各资产发放流水 |
| 流通量 | 当前各账户余额之和 |
| 已消费/已过期量 | Σ 消费 + Σ 过期 |
| 沉淀量 | 累计发行 − 流通 − 已消费 |

**约束**：

- 只有平台服务能调用发放接口，任何用户侧接口不得直接增加余额
- 转账只在账户间转移，转出方扣减 = 转入方增加，总量不变
- 每笔发行必须关联来源单据（订单 ID / 奖金记录 ID），可追溯

# 三、系统架构

## 3.1 分层

```
┌──────────────────────────────────────────────┐
│ 接入层  会员端（H5；APP 规划中）· 管理后台（Web）│
└──────────────────────────────────────────────┘
                    HTTPS
┌──────────────────────────────────────────────┐
│ 网关  Nginx · JWT · 限流 · 日志 · traceId     │
└──────────────────────────────────────────────┘
┌──────────────────────────────────────────────┐
│ 应用层（NestJS 模块化单体）                    │
│ user │ relation │ package │ order │ equity   │
│ wallet │ token │ bonus │ rank │ dividend     │
│ risk │ feature │ notify │ config │ audit       │
└──────────────────────────────────────────────┘
┌──────────────────────────────────────────────┐
│ 领域服务                                       │
│ TreeAggregator · BonusEngine · RankJudge     │
│ PoolAllocator · Scheduler · EventBus         │
└──────────────────────────────────────────────┘
┌──────────────────────────────────────────────┐
│ 基础设施  PostgreSQL · Redis · BullMQ · OSS   │
└──────────────────────────────────────────────┘
```

## 3.2 模块职责

| 模块 | 职责 |
|---|---|
| `user` | 注册、登录、实名、地址、状态 |
| `relation` | 关系树、path 维护、伞下查询、换绑审批 |
| `package` | 档位定义、升级价差计算 |
| `order` | 下单、状态机、发货、支付 |
| `equity` | 权益值账户、批次、抵扣、互转、过期 |
| `wallet` | 现金余额、流水、**互转** |
| `token` | 数权记账（只写不流转） |
| `bonus` | 五条奖金线计算与入账 |
| `rank` | 等级判定、升级日志、人数快照 |
| `dividend` | 分红池计算与分配 |
| `risk` | 设备指纹、同人多号、转账风控 |
| **`feature`** | **功能开关：全局 / 分级 / 分端，下发前端并拦截后端** |
| `admin` / `notify` / `config` / `audit` | 平台治理 |

## 3.3 技术栈

| 层 | 选型 |
|---|---|
| 后端 | NestJS 10 + Prisma 5 |
| 数据库 | PostgreSQL 14+ |
| 缓存/队列 | Redis 7 + BullMQ 4 |
| 会员端 | **Vue 3 + Vite H5；APP 端列入后续规划** |
| 管理端 | React 18 + Vite + Tailwind |
| 存储 | OSS |

## 3.4 部署

```
        CDN / WAF
            │
          Nginx
     ┌──────┼──────┐
  api-1   api-2   worker
     └──────┼──────┘
     ┌──────┼──────┐
PostgreSQL  Redis   OSS
  (主从)   (缓存/锁)
```

**worker** 专跑日结；日结必须单实例（Redis 锁 + DB 唯一键双保险）。

## 3.5 当前渠道与后续规划

**当前线上渠道为 H5；APP 端处于规划阶段。微信小程序与支付宝小程序不属于本项目渠道。**

| 端 | 状态 | 技术边界 |
|---|---|---|
| H5 | 当前已实现 | Vue 3 + Vite，浏览器路由、文件选择、链接分享 |
| APP | 后续规划 | 需要确定原生容器及登录、支付、推送、分享桥接后再实施 |

**代码分层**：

```
┌───────────────────────────────────┐
│ 会员业务层：页面 / 组件 / 状态 / 路由 │
├───────────────────────────────────┤
│ H5 适配：浏览器 API                 │
│ APP 适配：规划中的原生能力桥接       │
├───────────────────────────────────┤
│ 统一 API 层：登录 / 支付 / 上传 / 通知 │
└───────────────────────────────────┘
```

功能开关渠道只允许 `h5` 与 `app`。后台将 APP 明确标注为规划中；当前 H5 是唯一已接入渠道。

## 3.6 功能开关中心

**要求：所有功能模块运营后台可配置、可开关。**

**三层控制**：

```
① 全局开关（enabled）        → 关闭后所有端隐藏，后端接口拒绝
② 分端开关（platforms）      → 如"余额转账"仅 H5 开放
③ 分级开关（min_rank_level） → 如"分红池明细"仅副总及以上可见
```

**开关清单（会员端，全部可配）**：

| code | 功能 | 默认 |
|---|---|---|
| `package.purchase` | 礼包购买 | true |
| `product.mall` | 商品商城 | true |
| `member.upgrade` | 档位升级 | true |
| `member.repurchase` | 复消入口 | true |
| `referral.center` | 推广中心 | true |
| `team.view` | 团队查看 | true |
| `bonus.detail` | 收益明细 | true |
| `equity.account` | 权益值账户 | true |
| `equity.transfer` | 权益值转账 | true |
| `wallet.account` | 钱包余额 | true |
| `wallet.transfer` | 余额转账 | true |
| `token.view` | 数权查看 | true |
| `rank.view` | 等级信息 | true |
| `rank.dividend` | 分红池明细 | true |
| `notify.subscribe` | 消息订阅 | true |
| `realname` | 实名认证 | true |
| `customer.service` | 客服入口 | true |
| `address.manage` | 收货地址管理 | true |
| `transfer.password` | 转账支付密码 | true |

**下发与拦截机制**：

```
端启动 → GET /api/features?platform=h5
   ↓
返回当前用户可见的开关集合（已按 platform + rank_level 过滤）
   ↓
前端按开关渲染菜单与页面入口
   ↓
后端每个写接口二次校验（防止绕过前端直接调接口）
```

**三条硬性要求**：

1. **后端必须校验**：前端隐藏只是体验，接口层必须拒绝被关闭的功能
2. **变更立即生效**：Redis 缓存 5 分钟，后台修改后主动失效
3. **新功能必须先加开关**：任何新模块开发前先在 `feature_flags` 注册，不允许"裸奔"上线

# 四、数据模型

## 4.1 表清单（28 张核心表；当前 Prisma 运行模型 34 张）

| 域 | 表 | 数量 |
|---|---|---|
| 用户与关系 | `users`、`user_addresses`、`user_auth` | 3 |

# 五、核心流程

## 5.1 注册与绑定

```
扫码/点链接 → 解析推荐码
   ↓
校验推荐人 status = 0
   ↓
写 users：parent_id / path / depth / rank_level = 0
   ↓
注册成功
```

**边界**：推荐人不存在或注销 → `parent_id = NULL`；绑定后不可变更，换绑需审批。

## 5.2 下单

### 5.2.1 订单状态机（简化为 4 态）

```
CREATED（待支付）
   ├─ 支付成功 → PAID
   └─ 30 分钟未付 → CANCELLED
        ↓
PAID（已付款）
   ↓ 发货 / 交付
DELIVERED（已交付）
   ↓ 用户确认 或 T+10 自动
COMPLETED（终态，记录业绩）
```

**无退款**，因此无 REFUNDING / REFUNDED。COMPLETED 后即写业绩，次日日结计入。

### 5.2.2 四类订单

| type | 场景 | 业绩金额 | 直推奖 |
|---|---|---|---|
| 1 新购 | 首次买礼包 | 礼包价全额 | 100%，20 期 |
| 2 升级 | 低档升高档 | 差价 | 差价 × 100%，20 期 |
| 3 复消 | 权益值用完后再买 | 礼包价全额 | 10%，20 期 |
| 4 普通商品 | 商城购物 | **订单金额全额（含权益值抵扣）** | 无 |

**商品订单业绩口径**：按订单总额计入，不区分现金还是权益值抵扣。

### 5.2.3 支付方式

```
订单总额 amount
   ↓
可用：权益值（按到期日先扣）+ 钱包余额
   ↓
不足部分 → 微信支付
   ↓
amount = equity_deduct + balance_deduct + cash_pay
```

**扣减顺序**：权益值（快到期的先扣）→ 钱包余额 → 微信支付。

## 5.3 升级流程

```
选择升级档位
   ↓
差价 = 新档位价格 - 当前档位价格
   ↓
创建 orders（type=2, amount=差价, from_package_id=旧档位）
   ↓
支付 → PAID → 交付 → COMPLETED
   ↓
① users.package_id = 新档位
② 补发权益值：新权益值 - 旧权益值（不回收已用部分）
③ 创建直推奖：差价 × 100%，20 期
④ 业绩 = 差价
```

**举例**：

```
银卡 2,000（权益值 6,000，已用 2,000，剩 4,000）→ 升级金卡 5,000

差价       = 3,000
权益值补发 = 15,000 - 6,000 = 9,000
升级后可用 = 4,000 + 9,000 = 13,000
直推奖     = 3,000（分 20 期，每期 150）
业绩       = 3,000
```

## 5.4 每日奖金计算

### 5.4.1 主流程

```
每日 02:00（锁 lock:job:daily_settle:{date}）

Step 0  初始化结算批次（记录 step，支持断点续跑）
Step 1  幂等检查
Step 2  取昨日 COMPLETED 订单 → 写 order_performance
Step 3  树形归集 → 写 team_performance
Step 4  等级判定 → 更新 rank_id / rank_level / total_team_performance
Step 5  写 rank_snapshots（各等级人数 + 全网业绩 + 池子）
Step 6  计算团队奖
Step 7  计算平级奖 + 领导奖（自底向上）
Step 8  计算分红池
Step 9  拆分 70/30 → 写 wallet_transactions + token_lots
Step 10 标记完成
Step 11 通知
```

### 5.4.2 树形归集

```typescript
function aggregateTeam(
  users: { id: number; parentId: number | null; depth: number }[],
  own: Map<number, number>,
): Map<number, number> {
  const team = new Map<number, number>();
  // 必须按 depth 降序：子节点算完才传给父节点
  for (const u of [...users].sort((a, b) => b.depth - a.depth)) {
    const cur = (team.get(u.id) ?? 0) + (own.get(u.id) ?? 0);
    team.set(u.id, cur);
    if (u.parentId !== null) {
      team.set(u.parentId, (team.get(u.parentId) ?? 0) + cur);
    }
  }
  return team;
}
```

### 5.4.3 等级判定

```typescript
const total = user.totalTeamPerformance + todayTeamAmount;
const eligible = ranks.filter(r => total >= r.threshold).pop();
const newRankId = Math.max(user.rankId, eligible?.id ?? 0);   // 只升不降

if (newRankId > user.rankId) {
  await tx.user.update({ rankId, rankLevel, rankAchievedAt: now });
  await tx.rankLog.create({ from, to, total, triggerType: 'AUTO' });
}
await tx.user.update({ totalTeamPerformance: total });
```

### 5.4.4 团队奖

```
对每个 rank_level > 0 且 equity_status = 0：
    团队奖 = team_amount × rank.team_rate
```

### 5.4.5 平级奖 + 领导奖

```
按 depth 从深到浅遍历：

对每个 X：
  teamBonus = X.当日团队业绩 × X.费率

  P = X.parent_id
  if P:

    // 平级奖：首次满足即锁定
    if !X.peer_bonus_locked && P.rank_level <= X.rank_level:
        X.peer_bonus_locked = true
        X.peer_bonus_locked_at = now()
        audit('PEER_LOCK', X.id, P.id)

    if X.peer_bonus_locked && P.equity_status == 0:
        P.peer += teamBonus × 1.00

    // 领导奖
    if P.equity_status == 0:
        P.leader += teamBonus × 0.50
```

**三个易错点**：顺序不能反（基数依赖下级）；锁定必须持久化；上级暂停时锁定状态照常维护但不发钱。

### 5.4.6 分红池

```
G = 当日全网业绩
for rank where pool_rate > 0:
    count = 当日该级人数（快照）
    pool  = G × pool_rate
    perCapita = count > 0 ? pool / count : 0

对每个该级用户：分红 = perCapita
```

### 5.4.7 算例

```
全网当日业绩 1,000 万

A：总监(9%)，团队当日 10 万 → 团队奖 9,000
B：总监(9%)，团队当日 3 万，B 是 A 的直推且已锁定
   B 团队奖 = 2,700
   A 平级 = 2,700；A 领导 = 1,350；合计 4,050
C：副总(12%)，副总池 = 20 万，副总 10 人 → 分红 2 万
```

## 5.5 复消流程

```
每日 03:00 扫描 equity_accounts.balance = 0
  → users.equity_status = 1

会员复购 → orders(type=3, is_repurchase=true)
  → COMPLETED
  → 权益值入账 + equity_status = 0
  → 直推奖按 10% 创建计划
  → 业绩正常归集
```

**边界**：权益值全部过期同样触发暂停；恢复后不补发期间奖金。

## 5.6 资产转账

### 5.6.1 权益值转账

```
输入对方手机号 + 数量
   ↓
校验：双方正常、转出方实名、余额足够、未超限额
   ↓
按 expire_at ASC 扣 ACTIVE 批次
   ↓
创建 equity_transfers（PENDING）
   ↓
接收方确认（24h）
   ↓
转入方新建 lot（expire_at = 被扣批次最早到期日）
   ↓
双方写流水，状态 COMPLETED
```

### 5.6.2 钱包余额转账

```
输入对方手机号 + 金额
   ↓
校验：双方正常、转出方实名、余额足够
   ↓
balance -= amount, frozen += amount
   ↓
创建 wallet_transfers（PENDING）
   ↓
接收方确认（24h）
   ↓
转出方 frozen -= amount，入方 balance += amount
   ↓
双方写流水，状态 COMPLETED
```

**超时**：24h 未确认 → `EXPIRED`，退回转出方。

**风控规则**：

| 规则 | 阈值 | 动作 |
|---|---|---|
| 同设备互转 | 双方设备指纹相同 | 拒绝 |
| 高频互转 | 7 天内同一对账户 ≥3 次 | 人工审核 |
| 集中转入 | 24h 内收到 ≥3 人转入 | 人工审核 |
| 新号大额 | 注册 <7 天且单笔 >5,000 | 人工审核 |

# 六、关键机制

## 6.1 幂等

| 场景 | 幂等键 |
|---|---|
| 直推奖释放 | `UNIQUE(plan_id, period_no)` + `UNIQUE(biz_type, biz_id)` |
| 日结业绩 | `UNIQUE(user_id, stat_date)` |
| 分红 | `UNIQUE(stat_date, user_id)` |
| 钱包入账 | `UNIQUE(biz_type, biz_id)` |
| 权益值操作 | `UNIQUE(biz_type, biz_id, lot_id)` |
| 转账 | `transfer_no` + `idempotency_keys` |

## 6.2 快照一致性

日结三类快照，开始时锁定、全程复用：

| 快照 | 表 | 风险 |
|---|---|---|
| 当日订单 | `order_performance` | 中途订单变 COMPLETED |
| 各等级人数 + 全网业绩 | `rank_snapshots` | 中途有人升级 |
| 各人团队业绩 | `team_performance` | 中途新业绩 |

**窗口**：以自然日 `occur_date` 为界，02:00 处理前一天。

## 6.3 断点续跑

```
settle_batches：id, stat_date, step, status(RUNNING/DONE/FAILED), started_at, finished_at

Step 0 写批次(step=0)
每步完成更新 step
崩溃重启：从 batch.step 继续
```

**必须可重入**：每步重复执行结果一致（依赖幂等键）。

## 6.4 并发控制

| 场景 | 手段 |
|---|---|
| 日结 | Redis 锁 TTL 2h + DB 唯一键 |
| 余额扣减 | `UPDATE ... WHERE balance >= X AND version = ?` |
| 权益值扣减 | 同上 + 批次级 `remaining >= N` |
| 平级奖锁定 | `SELECT ... FOR UPDATE` |
| 转账 | 乐观锁 + 状态机 |

## 6.5 账务对账（每日 04:00）

```
① Σ(bonus_records.cash_amount) = Σ(wallet_transactions where type=1)
② Σ(bonus_records.token_amount) = Σ(token_lots.amount)
③ Σ(wallet_transactions.change_amount) = wallets.balance + wallets.frozen
④ Σ(dividends.amount) ≤ Σ(rank_snapshots.pool_amount)
⑤ Σ(equity_transactions.change_amount) = equity_accounts.balance
任一不等 → 告警
```

## 6.6 监控指标

| 指标 | 阈值 | 动作 |
|---|---|---|
| 日结耗时 | > 10 分钟 | 告警 |
| 日结失败 | 任一 | 立即告警 |
| 对账差异 | > 0 | 告警 |
| 奖金支出 / 当日业绩 | > 60% | 预警 |
| 转账风控命中率 | 突增 300% | 告警 |
| 单日新增会员 | 环比 > 300% | 风控告警 |

# 九、非功能要求

## 9.1 性能

| 指标 | 目标 |
|---|---|
| 日结（10 万用户） | < 3 分钟 |
| 树形归集 | O(N)，10 万约 1 秒 |
| 伞下查询 | < 300ms |
| 接口 P95 | < 300ms 读 / < 800ms 写 |

## 9.2 可用性

主从 + 每日全量 + WAL，RPO < 5min；双节点 + 健康检查；Redis AOF；日结可重跑。

## 9.3 安全

HTTPS；手机号/身份证 AES-256-GCM 加密；RBAC；资金操作全审计；日志脱敏。

## 9.4 测试要求

**必测场景**：

- [ ] 同一分期并发触发 10 次，只入账 1 次
- [ ] 日结中断后从断点续跑，结果与一次跑完一致
- [ ] 平级奖锁定后，双方任意升级都不影响发放
- [ ] 上级暂停计酬时，下级业绩仍计入，但上级不领钱
- [ ] 分红池某等级人数为 0 时不除零
- [ ] 权益值批次 FIFO 扣减、过期、转账继承到期日
- [ ] 升级补发权益值差额正确
- [ ] 钱包余额转账在确认前不扣减、超时正确退回
- [ ] 同一资产并发转账，不出现负余额
- [ ] 用转账所得余额下单，业绩正常计入（不追踪余额来源）
- [ ] 开关关闭后前端入口隐藏、后端接口拒绝
- [ ] 分端开关在不同 platform 下表现正确、分级开关按等级过滤

## 11.2 术语

| 术语 | 说明 |
|---|---|

| 数权 | 奖金的 30%，仅记账 |
| 只升不降 | 等级达到后永久保留 |
